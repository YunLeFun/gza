# 双人电驴与僵尸突围实施计划

2026-10-11 整合更新：当前「僵尸突围」统一为城市中的 1–4 人活动，寻找电动车、驾驶、双座共乘与停车下车成为同一局的操作。本计划保留旧双座固定路线交付过程和历史验收记录；旧房间与邀请经 `/coop-legacy.html` 兼容，旧阶段记录不代替新 v3 规则验收。当前能力见[僵尸突围](city-zombie-coop.md)，历史规则见[双座路线兼容记录](zombie-coop.md)。

状态：阶段 1–3 已实现，阶段 4 的合作模式本地检查已通过；生产 Play 合作房与 CloudBase 签票已部署，并通过两个专用测试客户端的真实签票与房间冒烟。真实 Steam 跨设备验收待正式 App ID 与设备，网页实际部署版本、真人登录及目标设备完整对局仍需确认，生产带宽与负载尚未验收。日期：2026-10-09。最新证据见 [合作战斗发布验证](releases/2026-10-09-coop.md)。

目标：两名玩家共乘一辆电动车，一人驾驶、一人后座射击，完成一局约 5–8 分钟的短路线突围。先交付可游玩的载人与打靶原型，再接入联机和僵尸关卡。作为 GZA 的独立挑战入口，按需加载。

## 已采纳的产品决策

| 决策 | 已采纳方向 | 对实施的影响 |
| --- | --- | --- |
| 首发联机路径 | Steam 桌面好友房优先；Web 后续适配同一规则核心 | Steam 主要在本仓库开发，真实验收需要正式 App ID 与两个账号／设备；Web 需要同步修改 `play` 服务、签票、本仓库 BFF 和 SDK |
| 载人车型 | 同时支持单座与双座，现有车型增加双人套件；双座收起配送箱及占用后座的音箱／货架 | 单座保留原配送外观；双座使用长坐垫、后脚踏和扶手，切换复用已创建模型 |
| 座位与上下车 | 开局选座，补给点停车后可换座 | 不需要首版同时实现多人步行与地面战斗；若要求自由上下车，增加人物移动、登车竞争、落脚检查及掉队处理 |

用户已要求遵循建议实施，并明确单座与双座均需支持。首发联机平台与换座方向按上述建议推进；真实 Steam 验收前仍需正式 App ID、测试账号与设备。当前已完成模型、真实开发双客户端与 Steam 合作房代码，真实 Steam 平台连接不视为已通过。

其余暂定值可在打靶和试玩阶段调整：首版两人、一辆车；桌面键鼠和手柄优先；乘客正常坐姿与肩后瞄准镜头；两位玩家使用各自角色外观，车体外观由当前驾驶员决定；卡通、夸张击退、无血腥；首版不造成友军伤害。手机合作、四人两辆车、单人 AI 后座和自由步行战斗列入后续阶段。若这些能力必须首发，需要补充范围。

## 实施前的基础与缺口（启动时基线）

以下描述本计划启动时的代码状态；共享世界载具、乘客锚点与独立合作协议现已按阶段 1–3 补齐。

### 电动车与角色

- [电动车外壳](https://github.com/YunLeFun/gza/blob/main/docs/.vitepress/game-reference/apps/dayun-kicker/src/render/scooterBody.ts)与[骑手](https://github.com/YunLeFun/gza/blob/main/docs/.vitepress/game-reference/apps/dayun-kicker/src/render/riderRig.ts)均由 Three.js 本地几何生成，现阶段沿用程序模型。
- 当前坐垫长 0.66、中心 Z=0.27，司机骨盆 Z=0.22；后方约 Z=0.93 有配送箱。货架本身高于坐垫，部分皮肤另有后置音箱；需一起调整。
- [布局参数](https://github.com/YunLeFun/gza/blob/main/docs/.vitepress/game-reference/apps/dayun-kicker/src/config/render/rider.ts)有车把、轮轴与司机骨长，没有乘客座位、脚踏、扶手或枪口锚点。
- [座舱](https://github.com/YunLeFun/dayun-kicker/blob/main/apps/dayun-kicker/src/render/cockpit.ts)挂在相机下，带第一人称视口适配；不能直接用它代表两位玩家共享的世界载具。[联机对手](https://github.com/YunLeFun/dayun-kicker/blob/main/apps/dayun-kicker/src/render/onlineOpponent.ts)当前是独立线框模型。
- [上下车](https://github.com/YunLeFun/dayun-kicker/blob/main/apps/dayun-kicker/src/district/vehicleInteraction.ts)属于单玩家载具切换。骑行胶囊与停车车体碰撞并非统一双人车辆形状，需重新验证双座车尾、转弯与上下车净空。

### 联机与射击

- [Steam 好友房](steam-multiplayer.md)已有大厅、邀请、准备、消息序号、断线处理，以及房主主进程 60 Hz 模拟／20 Hz 快照框架；真实连接验收仍待正式 App ID 和多设备。
- [现有协议](https://github.com/YunLeFun/dayun-kicker/blob/main/packages/dayun-kicker-desktop-bridge/src/multiplayer.ts)面向竞速 `x + distance`，没有完整街区位置、共乘座位、瞄准、动态敌人与枪械。合作模式需要新消息和规则。
- Web / Play 当前是独立的竞速房间，默认 60 Hz 模拟／10 Hz 快照；不能把 Steam 的 20 Hz 当作网页既有配置。新增网页合作房间需要新房间注册与 ticket audience，并同步 BFF／SDK。
- 坦克的命中查询、开火反馈及部分资源组织可复用；慢速抛物线炮弹与建筑伤害规则不能直接作为后座枪械。
- 街区模拟目前受渲染循环与本地菜单暂停控制。合作房间需独立权威循环，某一客户端打开菜单不能冻结所有玩家。

## 实施原则

1. 车辆、座位、敌人、命中、弹药及关卡状态由权威模拟拥有，Three.js 只负责显示。规则核心不依赖 DOM、Steam 或 Colyseus。
2. 一辆车辆只同步一套姿态。两位角色的位置由车辆姿态和座位局部坐标推导，避免后座单独插值造成脱座。
3. 司机与后座输入分开。驾驶、换座、开火均由权威端核对身份和座位；换座是原子操作，不能让两人同时占同一座位。
4. 世界车辆与第一人称显示共用布局、几何工厂和皮肤配置，第一人称适配保留独立镜头；只提取本模式需要的边界，不一次重写整个街区。
5. 启动阶段建立新模式入口与协议版本，逐步交付并回归经典竞速、单人上下车和车库外观。

## 阶段 2：双人共乘同步

交付：两个客户端能进房、选择不同座位、准备、开始、驾驶和射击；允许房主选择任一座位。

- [x] 新增独立合作输入／快照与房间模式标识，复用现有 transport 和大厅生命周期。
- [x] 以 matchId 标识本局唯一共享车辆；规则状态包含两个座位的玩家 ID、位置／高度／朝向／速度、瞄准方向、弹药、射击 ID、输入序号和模拟 tick。
- [x] 权威循环处理驾驶、座位权限、敌人与命中；前台渲染暂停不停止房主模拟。
- [x] 车辆预测／校正与远端插值独立于视角；射手立即获得本地开火反馈，伤害与击杀等待权威确认。
- [x] 基于 observedTick 建立有界目标／车辆历史，最多回查 15 tick / 250 ms；旧序号、重复射击、越权输入和乱序快照不能重复改变状态。
- [x] 可靠消息传递准备、换座、关卡切换和结算；持续姿态使用有界快照与事件去重。
- [x] Steam 与开发 WebSocket 分别使用 60 Hz 模拟／20 Hz 快照，并验证双客户端同步。
- [x] 生产 Play 合作房与 CloudBase 签票接入并部署；两个专用测试客户端通过真实签票链完成创建／加入、准备／开始、整匣射击、换弹与主动断开，房间和连接回收为 0。见 [2026-10-09 生产后端验证](releases/2026-10-09-coop.md#生产后端)。
- [ ] 确认实际网页／BFF 部署版本与生产玩家会话，测量部署端 RTT、带宽和负载，并完成目标设备完整对局。

断线草案：开局后首版不接受新玩家；任一队员断线则停止本局驾驶／射击、显示原因并结束本局，重新组队重试。停止后释放所有持续输入。房主退出结束房间，主机迁移和断线重连另行设计。

验收：房主驾驶和房主射击两种组合都可玩；两个客户端车体、座位、命中及弹药一致；座位冲突被拒绝；菜单、切后台和断线行为明确；模拟网络覆盖延迟、丢包和消息乱序。模拟测试与真实平台连接验收分别记录。

## 阶段 3：短路线僵尸突围

交付：一局约 5–8 分钟，有出发、补给、尸潮与撤离，以及明确成功／失败结算。

- [x] 复用城市美术元素，制作独立 5.4 km 平地突围道路，确认出生点、三处补给和撤离点；只加载本局内容。
- [x] 加入普通僵尸和跑动僵尸，两种武器暂定冲锋枪与霰弹枪。初版用原创简化程序模型。
- [x] 敌人实现生成、追逐、攻击、受击、死亡和回收；数量、碰撞与特效均有上限，实测后确定并发上限。
- [x] 以道路障碍、追击敌人与停车补给形成压力，司机通过路线、速度和近身清障参与战斗。
- [x] 定义共享车体耐久、弹药补给与失败条件；补给点按权威停车条件自动领取一次补给，换座单独由双方确认，不必引入多人步行。
- [x] 用共享 UI token、GameMetric、GameNotice、GameButton 展示目标、耐久、弹药、伙伴座位与结算；保留键盘、手柄焦点及输入释放。
- [x] 合作结算使用独立本局统计；首版不接入竞速排行榜、云端奖励或收费权益。

验收：两人均有持续决策；交换座位后操作易理解；能完整胜利、失败和重试；暂停菜单不会影响伙伴模拟；命中、击杀、补给及结算只发生一次。

## 阶段 2–4 本地验证记录（2026-10-09）

已实现独立合作入口、共享纯规则、Steam 双人房与真正的开发 WebSocket authority。最终合作单测 99 项及音效／main／preload／Steam／双座模型相关单测 47 项通过；覆盖完整 5.4km 胜利、权限、射击遮挡／去重、250ms 命中历史、补给、换座、输入超时、断线与胜负；12 场 Steam 模拟延迟／丢包矩阵通过。输入／资源清理修复后的四项双浏览器 GPU E2E 全部通过，验证两种房主座位、同步、换弹、菜单输入释放、真实 WebGL 连接丢失／恢复、断线重组及 390×844 触屏。补充首轮输入与换座武器时序回归，并验证退出时释放画布。手机首页 ready-menu 两项回归通过。合成满池战斗 GPU 为 136 calls / 30,080 triangles，平均 16.46ms、P95 16.80ms。

本地阶段的全仓类型检查、Web／桌面构建及 Web 性能预算与发布产物校验通过（221 文件）：合作入口 314.0 KiB gzip / 350 KiB，CSS 5.1 KiB / 16 KiB，完整资源 12.44 MiB / 20 MiB；打包资源预算相关 9 项测试通过。生产 Electron 合作入口 E2E 1/1 通过，核对合作页、标题栏、可信桥接、App ID 0 离线提示、无 DEV 入口及返回单座首页。这些为本地阶段快照；同日后续发布候选的最终类型检查、1034 项单元测试、剧情校验、构建、打包预算与 365 文件产物校验通过，生产 Play／CloudBase 签票链也已验证，详见[发布记录](releases/2026-10-09-coop.md)。

本地阶段曾记录街区冷启动 21,230 ms / 15,000 ms，以及四项既有街区桌面绘制预算 E2E 失败。同日后续工作区优化已通过街道与全部总部机位的原绘制预算回归；冷启动最终 Metal 样本仍为 16,671–17,362 ms，原样性能配置的 SwiftShader 样本为 39,274 ms，继续未达到 15 秒。详见[后续渲染与冷启动复测](rendering-performance.md#2026-10-09-跨格合批与冷启动复测)，不能记为全部 E2E 或性能验收通过。实际 Steam 双设备、跨网络、实体手机、Windows / Steam Deck 尚未测试；真人账号 SSO、网页实际部署回执以及生产带宽／负载与目标设备完整对局仍待验收。详细操作和验证边界见[僵尸突围](zombie-coop.md)。
