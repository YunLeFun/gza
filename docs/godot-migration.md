# Godot 完整迁移计划

决策日期：2026-10-16。目标引擎确定为 Godot；执行顺序为 **第一章与一个完整街区 → 原生发行验收 → 地图分块加载 → 逐区扩城**。本文是实施计划，不代表功能、性能或发行已经验收通过。

应用显示名保持《GZA：暴力电驴》，仓库、包名、应用 ID、账号和既有存档标识继续使用 `dayun-kicker`。游戏源码仍在原私有仓库；本次迁移不涉及公开源码或搬迁仓库。

实施状态见[迁移进度与验收记录](godot-migration-progress.md)：M0–M1 工程和午餐切片已落地，M2 已接入七单首章与客村 / TIT，可玩候选与验证边界见 [M2 记录](godot-m2.md)。维护者已明确将 Windows 实机测试后置，因此允许先实施当前功能切片；G1.3 / G2.0 的 Windows 运行验收仍开放，不据此切换生产入口。

第一目标是 Steam Windows x64 的离线单人版；macOS 用于当前开发和回归，通过独立打包与签名验收后才列为发行平台。Linux / Steam Deck、手机、原生线上账号与多人分别验收，不绑定第一章工期。

| 阶段 | 可交付结果 | 开始下一阶段的条件 |
| --- | --- | --- |
| M0 基线与契约 | 功能清单、完整冻结版本、首章地点范围、兼容与验收矩阵 | 明确哪些迁移、哪些后续恢复，记录目标机器和既有门槛 |
| M1 原生工程 | 可重复构建的 Godot 工程、资源导入、物理与任务数据接口、Windows 薄包 | 干净环境能恢复资源、导出并运行包含原生物理扩展的小场景 |
| M2 第一章与完整街区 | 客村 / TIT 生活街区、完整「粥还热」、菜单与存档、通关后继续游玩 | 全章连续实玩、关键分支与恢复、街区循环及原生输入通过 |

Godot 是后续原生开发方向。Three.js / Electron 在 M3 通过前继续作为可运行的对照与回退版本；不同时新增两份首章剧情。现有 Web 试玩、账号与后端继续运作，Web 后续只维护明确的试玩范围。M3 的“默认客户端切换”与“所有历史功能迁完”分别记账，后者需要完成 M6 清单。

### 双宿主分工

决策日期：2026-10-17。Godot 承载完整游戏，Three.js Web 承载吸引下载的即点即玩展示；不以 Godot Web 导出替代 Web 宿主。

| 宿主 | 定位 | 新功能如何落地 |
| --- | --- | --- |
| Godot 原生 | 完整游戏：章节、城市生活与环境车流、存档、设施、合作和平台服务 | 新玩法与系统先在此实现并验收 |
| Three.js Web | 即点即玩试玩与展示：精选街机赛事、街景与夜景片段、手机打开与分享、下载引导；同时是 TS 程序美术的源头 | 只加入服务展示与转化的片段，不追平完整功能 |

不采用 Godot Web 导出作为同构方案：工程使用 Forward+，Godot Web 只支持 Compatibility（WebGL2），夜景与描边会降级；Rust Rapier GDExtension 的 wasm 构建仍属实验路径；引擎 wasm 与 PCK 远超 Web 资源预算，手机浏览器首载代价高。条件变化时可另做实验，不作为发行依赖。

两端共享以下三层，避免逐步分叉：

1. **美术**：TS 程序模型是唯一源头，构建期导出 GLB 供 Godot 导入。
2. **内容与数值**：`dayun-kicker-content` 数据包和章节 / 配送 / 节点图 fixtures。
3. **规则**：写成规格与两端共用的 fixtures，各自实现并逐条对照；计算密集且需确定性的模拟，在 Web 确需完整运行时再下沉到可同时编译 GDExtension 与 wasm 的 Rust 核心。

### 一个街区与完整第一章如何同时成立

完整打磨街区定为 **客村 / TIT 骑手站及周边生活圈**。M0 用现有道路、任务点和可达边界冻结具体多边形与地点清单，不用任意面积替代可玩范围。

第一章仍从客村开始、在陈家祠南门结束，保留丽园雅庭、滨江、取药点、两条解药路线和祠堂任务。M2 使用固定的章节地图包，保留这些地点之间必要的可骑行道路、碰撞、任务点和远景；完整生活内容先集中在客村 / TIT。章节以外未完成区域保留明确边界，不承诺整座广州已经可玩。

M2 不引入通用运行时地图流式系统，不用传送、改地点或跳过路口代替连续骑行。先通过构建期裁剪与固定资源包控制规模；若章节路线资源超预算，先处理资源和场景表达，再推进。通关后可继续游玩已经交付的街区与章节路线。

## 3. 生产工程与复用方式

生产工程已落在原源码仓库的 `apps/dayun-kicker-godot/`，保留 `experiments/dayun-kicker-godot/` 作为历史验证入口。以下是当前 monorepo 布局；M2 已补章节和步行，平台接口后续按里程碑补齐。不把实验的临时导出、helper、压力默认值和本机路径整体搬入生产。

原生业务默认使用带类型标注的 GDScript；Rust GDExtension 先保留已经验证的 Rapier 查询与必要计算。TypeScript / Node 留在构建工具和现有服务端，不作为原生游戏运行依赖。新增原生优化须有实际热点证据。

```text
apps/dayun-kicker/          # Web / Three.js 宿主
apps/dayun-kicker-desktop/  # 既有 Electron 宿主
apps/dayun-kicker-godot/    # 原生 project.godot / export_presets.cfg
  scenes/                  # 启动场景
  scripts/game/            # Session、配送与存档
  scripts/world/           # 固定地图；M4 才实现分块调度
  scripts/player/          # 骑行
  scripts/ui/              # Control / Theme 与焦点导航
  native/                  # 扩展声明；动态库留在忽略目录
  generated/               # 构建期生成的内容，忽略
  tests/                   # 行为、存档、连续骑行与包检查
packages/dayun-kicker-content/ # 共享目录、规则、类型与范围
packages/dayun-kicker-physics/ # 固定版本 Rust Rapier 源码与锁文件
scripts/godot/             # 冻结、内容导出、构建、测试与包检查
```

媒体、扩展动态库、导入缓存及导出包的位置须先加入忽略规则；上述树不表示允许把二进制提交进 Git。

| 现有实现 | 处理方式 |
| --- | --- |
| 地图 JSON、道路节点、地点 ID、模型 / 音频来源 | 复用数据和许可；导入时记录坐标、地图版本、单位与 hash |
| TypeScript 程序模型与导出脚本 | 先作为构建工具使用，产出固定场景资源；游戏运行不启动浏览器或 Vite |
| 配送、职业、制服、背包、剧情门槛 | 导出规则与 fixtures，移植原生逻辑；按行为对照，不能直接执行 TS |
| ADV.JS 对白源 | 保留单一内容源，构建期导出首章所需的中立指令与条件数据；原生执行已列明的子集，不支持的指令构建失败 |
| Vue / Reka UI | 用 Godot Control / Theme 重建呈现，映射既有 token；沿用交互语义、稳定操作 ID、文本与焦点用例 |
| Three.js 材质与后处理 | 改用原生材质 / shader；保留同画质对照与视觉差异清单 |
| Electron preload、文件存储、Steam Node 模块 | 接口迁到原生平台适配；Node 二进制不直接复用 |
| BFF、CloudBase、Play 服务与协议 | 保持服务端规则；后续实现原生客户端，不复制浏览器会话或重写服务端来迎合客户端 |

采用少量职责明确的 Module，Interface 同时约束调用顺序、失败、版本及状态：`GameSession` 管当前模式和暂停；`ChapterDirector` 处理章节点；`DeliveryRules` 校验实际取送并结算；`WorldState` 持有稳定实体与任务变化；`SaveStore` 处理版本 / 原子保存 / 迁移；M4 的 `WorldLoader` 才负责资源生命周期。UI 发送意图和显示状态，不发奖励、不改物理。

剧情执行只允许宿主白名单命令，宿主再次核对地点、订单、交付记录和幂等键。禁止对白直接设置通关或发奖；不嵌入 JavaScript 运行时来复用 Vue / ADV.JS。先覆盖首章实际指令和表达式，不先重造完整叙事引擎。

以[首章设计](story-chapter-one.md)为规则来源，保留七个现有订单 ID、对白语气、任务门槛与据点进度，不用三单配送 demo 替代。

## 7. M4：在已有地图上实现分块加载

M2–M3 通过后，先把**相同内容**改成分块，验证前后任务、道路、碰撞、画面和存档一致，再新增地理内容。已有静态合批网格、256 米碰撞窗口、启动分段构建都不等于完整流式系统。

### 数据与加载生命周期

维持既有“约 1 km 地图单元”的内容 / 分发方向；运行时渲染、碰撞子块可更细。以 256 / 512 米作为性能实验候选，不提前承诺固定尺寸或把 128 米合批范围直接当资源块。

- [ ] **G4.1** 定义 `CityManifest` / `CellManifest`：城市和坐标原点、cell ID / 包围盒、版本 / hash / 依赖、资源 / 碰撞 / 导航索引、全局实体 ID、跨块道路与任务引用、LOD 和构建成本。重复地物有唯一所有者；桥梁 / 河岸跨块几何按同一切分规则保留连续性。
- [ ] **G4.2** 实现 `WorldLoader`：`unloaded → requested → loading → prepared → activating → active → retiring → unloaded`；每个请求携带版本 / generation，取消后到达的旧结果不得挂入新世界。状态和错误可观测，失败保留重试入口与当前可玩区。
- [ ] **G4.3** 后台只做安全的数据准备与资源请求；资源已完成才获取，节点接入、碰撞 / 导航同步和 GPU 相关工作按帧预算分批提交。后台读取完成不等于已经可通行。[官方后台加载说明](https://docs.godotengine.org/en/stable/tutorials/io/background_loading.html)
- [ ] **G4.4** 按位置、速度、朝向和路线预取；优先碰撞 / 支撑面 / 必要导航，再开放玩家进入，之后补近景和装饰。预取距离至少覆盖速度乘加载耗时及安全余量；加载赶不上时用明确安全边界等待，不允许先驶入空地再补碰撞。
- [ ] **G4.5** 对玩家、当前骑乘 / 停放车辆、活跃剧情、追逐 / 战斗、室内出口和跨块公交建立驻留引用；设硬上限及退出机制，避免任务 pin 整条路线导致无限驻留。只保留任务地点元数据，不为未来交付常驻整段地图。
- [ ] **G4.6** 跨块只更新实体归属，不复制实体；接缝的道路 / 导航连接在可用版本上原子切换。不可达目标明确返回失败，不每帧对整城重规划；导航结构保持简化和固定全局道路索引。[官方导航性能说明](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_optimizing_performance.html)

### 卸载、坐标与持久化

- [ ] **G4.7** `WorldState` 持有存档状态，场景节点只投影状态；卸载前记录已结算事件、任务 / 据点变化、物品与车辆归属。释放节点、计时器、信号、碰撞 / 导航、MultiMesh 和独占资源引用；共享资源按引用计数回收。
- [ ] **G4.8** 对远处交通 / 行人使用明确的简化模拟规则；活跃任务与战斗区域保留已承诺的物理和规则频率。任何模拟简化单独对照，不拿减少 AI 或碰撞工作量冒充同负载提速。
- [ ] **G4.9** 存档采用稳定城市坐标、cell ID 与局部坐标；地图版本不同先走迁移映射，缺块提供安全恢复。渲染原点变化不能改世界 ID、任务距离或联网位置。先测既有地图范围精度，再决定是否需要原点移动 / 大世界坐标；不直接把经纬度当场景米制坐标。[大世界坐标说明](https://docs.godotengine.org/en/stable/tutorials/physics/large_world_coordinates.html)

### M4 出口验收

- 同一章节在固定包 / 流式包分别通关，订单、奖励、关键世界状态一致；两个解药路线和跨桥骑行都通过。
- 最高合法速度连续穿越、掉头、斜向跨四块、跨块上下车 / 追逐、室内返回、边界存读档；不坠落、不穿墙、不重复人物、任务不丢失。
- 单次失败、缺块、hash 错误、依赖缺失、旧请求回调和版本更新不会破坏已激活世界；离线安装包运行不依赖 COS 网络。
- 同一跨块路线往返至少 20 次，外加不少于 30 分钟持续游玩；记录驻留 cell、资源引用、碰撞数、CPU / GPU / RSS 和启动时间，热身后不得随累计访问区域持续增长。
- 在 M0 冻结的内存 / 驻留上限和性能标准内通过。块大小、单帧激活时间和预取量经数据确定；本计划不凭空宣布目标机器能加载多少块。

既有 Godot 压力门槛保留：正式窗口 **最低完整一秒帧数 ≥60、P99 ≤16.667 ms、零 >50 ms 长帧**。普通首章与压力场景分别报告，不混合不同敌人数、HUD、存档或锁血配置。已有增强档画质和实际 1821×1138 / 4×MSAA 对照继续保留；其他设备另列其实际画质与缓冲，不通过降质通过旧条件。

新增首章、跨块的冷启动、内存及实机配置预算在 G0.2 测量现状后、实施前固定；未确定项记为“待冻结”，不能算通过。不得提高已有门槛来消除失败。性能候选遵守三层反馈：逻辑 → 真实短窗筛选 → 通过后才跑三单 / 长途完整验收。M2 首章功能可在性能尚未过关时做内部验证；M3 切换、M4 正式启动和内容扩城需要前序出口通过。

优先复用 `benchmark:camera` 的输入 / 路线与报告语义、Godot 三层测试、存档 / 章节 fixtures 和原生显示回归。新增首章 / 流式测试入口需明确标注为待实现，不把浏览器 E2E 原样套到 Godot。profiler、trace、截图和诊断 helper 与正式计时窗口分开；失焦、绘制停滞、后台负载或冻结校验失败的样本保留并拒收。
