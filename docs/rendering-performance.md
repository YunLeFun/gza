# 街区渲染性能优化（2026-10-08）

后续优化的优先级、复测命令、验收规则与 Goal 模板见[游戏性能优化手册](game-performance-playbook.md)。本文保留各轮实现、实测与验证边界。

省二医附近的桌面骑行缓存帧原为 337 次绘制，超过已有 300 次门槛。本次按实际绘制来源优化座舱和短跨桥护栏，桌面降至约 234 次，减少约 31%；医院骑行与步行视角都按原有 `<300 calls / <90,000 triangles` 断言，不提高预算。

## 改动与代价

- `render/cockpitBatch.ts` 合并车身、转向架、握把和刹车各自的刚性零件；仪表盘、刹车转轴、动态线管和可选皮肤继续保留各自的更新／可见性边界。
- 手臂、手指和腿部的方盒零件按共享材质实例化，沿原有动画骨架更新实例矩阵。姿态不变时不上传矩阵；下车、游览和进入建筑时不更新隐藏的骑手实例。座舱绘制从 67 次降为 33 次，几何数量保持一致。
- 原来每约 4 m 独立绘制的道路跨水护栏，改按 120 m 空间格合批，保留每段破坏 ID 和几何范围。碰撞、单段破坏和恢复继续使用原契约。
- 护栏格使用 470 m 保守可见半径，覆盖原先每段 380 m 的范围，因此可能多画邻近格内的护栏。缓存帧三角形从约 64,500 增至约 68,000，换取更少提交；没有简化医院、降低分辨率或修改水面刷新质量。

## 预算与实测

继续以桌面 60 fps（16.7 ms／帧）、手机 30 fps（33.3 ms／帧）为目标。缓存帧门槛和水面捕获刷新帧分别统计，不能用暂停后的缓存数值代表所有运行帧。

基线与缓存回归使用桌面 1440 × 900、手机 390 × 844 的浏览器视口，均设置 720p / 30 fps、晴天正午，医院西侧停稳后暂停并等待水面捕获稳定。绘制总数包含世界、阴影、第一人称和最终呈现；车流等变化会带来少量波动。

| 骑行缓存视角 | 优化前调用 | 最终回归调用 | 最终回归三角形 |
| --- | ---: | ---: | ---: |
| 桌面 | 337 | 234 | 67,810 |
| 手机 | 216–218 | 182 | 58,416 |

最终步行缓存帧：桌面 228 次／65,812 三角形，手机 174 次／55,634 三角形。此前优化采样中手机骑行为 177–182 次，差异来自可见车流等变化。

运行采样使用本机 **Apple M1 Pro / ANGLE Metal**，两个视口串行运行，开始状态确认为 `playing`，医院西侧停稳、热身 3 秒后各采样 120 帧。桌面设置 1080p / 60 fps，实际绘制缓冲 1440 × 900；手机设置 720p / 30 fps，实际缓冲 390 × 844。使用一条 GPU 查询覆盖整帧提交，包含反射、折射、阴影和呈现。

| 运行采样 | 桌面视口 | 手机视口 |
| --- | ---: | ---: |
| 平均帧率 | 60.0 fps | 30.0 fps |
| 帧间隔中位数 / P95 | 16.6 / 17.7 ms | 33.3 / 34.0 ms |
| GPU 整帧中位数 / P95 | 4.65 / 8.41 ms | 1.77 / 3.75 ms |
| 采样内最大调用（含水面捕获） | 294 | 222 |
| 采样内最大三角形 | 78,278 | 67,152 |

这些结果证明该机位在本机的提交数量和短时帧率；不代表整个地图、连续高速行驶或实体手机表现，也不能据此声称帧率提升了 31%。帧间隔包含 CPU、GPU、限帧和系统调度；GPU 查询只测提交范围的 GPU 工作，不能与 CPU 提交耗时直接相加。

## GPU 与复测

游戏的 WebGL 渲染本来就在浏览器 GPU 上运行。实例化把多份几何的绘制交给 GPU，减少 CPU 提交；本次没有把 Rapier 物理迁移到 GPU，也没有新增云 GPU 服务。

本地原生 GPU 浏览器检查使用单 worker：

```sh
pnpm exec playwright test e2e/hospital.spec.ts e2e/jianghai-interchange.spec.ts e2e/water-rendering.spec.ts e2e/vehicle-interaction.spec.ts --config playwright.gpu.config.ts
```

`playwright.gpu.config.ts` 在 macOS 使用完整 Chromium 与 ANGLE Metal；其他平台使用完整 Chromium 的自动后端。以附件中的 `gpu` 字段确认实际设备，不能仅凭配置文件判断 GPU 已启用。普通 CI 配置保持原样；性能采样与其他 WebGL 测试串行运行，避免争用同一 GPU。

开发街区页面新增临时采样接口：

```js
// 整帧 GPU 耗时、帧间隔及各阶段的 CPU 提交／绘制数
const profile = await window.__DISTRICT_DEBUG__.profile(120);
// 需要定位 GPU 阶段时另做一次采样；不与上一次重叠
const passes = await window.__DISTRICT_DEBUG__.profile(60, "passes");
```

默认结果的 `gpuFrameMs` 为整帧 GPU 时间；`samples` 按世界、座舱、反射、折射、呈现分组，并单列阴影提交。`"passes"` 模式改测各阶段的 `gpuMs`，不将阶段之和当作整帧测量。第一帧保存实际绘制对象名，方便定位碎片网格。`EXT_disjoint_timer_query_webgl2` 不可用、上下文丢失或计时无效时保留 `null`，不使用阻塞式 `finish` / `readPixels` 补测。

采样结束或超时会恢复所有钩子、释放查询；未采样时没有持续查询工作。接口只随开发诊断模块加载，发布产物校验检查诊断代码未进入生产构建。

## 2026-10-09 静态合批可见面剔除

本节记录首轮优化及其当时的验证结果；同日继续处理跨格合批和冷启动的结果见下一节。

本次继续处理已记录的街区三角形超限。120 m 楼体合批只要部分进入视野，原来就会提交整批窗格和檐台；远处广州塔也提交整段轮廓的背面。通用楼体详细批次和广州塔基础轮廓现在按每个实际渲染相机选择原部件，保留与视锥相交的包围盒，再依据材质的 FrontSide / BackSide / DoubleSide 选择可能栅格化的原始三角面。没有减少模型细节或修改预算。

`render/staticBatch.ts` 的可选 `cameraCulling` 仅在上述两处启用；`staticBatchCulling.ts` 预计算部件边界和三角面平面，复用同一索引缓冲。主画面、反射和折射使用各自相机；阴影使用阴影相机及实际深度材质的面向规则。初始索引、完整模型边界和破坏 ID / 几何范围保留，相机空子集不隐藏整张网格，后续视角与毁坏恢复可以重新选择。相同投影和材质状态复用上一结果，逐帧不创建数组或向量。诊断采样的首帧 `draws` 同时记录实际 calls 和 triangles，方便继续定位开销。

## 2026-10-09 跨格合批与冷启动复测

街道、交通设施和通用楼体详细网格现在跨空间格共享静态绘制，保留原格和破坏对象的可见性。水面层仍先按原格分类，再合并相同材质、层、阴影和属性的网格；动画灯光、碰撞和破坏范围继续独立。琶洲地标基础与详细网格也启用各实际相机的部件和面剔除。腾讯跨街的旧日景基线为 347 calls / 95,152 triangles，夜景为 348 / 95,710；原用例先在调用断言失败，三角形也超限，不能只记录调用数。

最终预算用例按每帧采样 800 ms，覆盖 5 Hz 水面刷新及阴影和座舱。街道三个机位、昼 / 晚 / 夜及两轮热资源复测共 18 组均通过，最高 252 calls / 82,224 triangles，每组采到 41–49 帧。总部七个机位的昼夜共 14 组均通过，最高 259 calls / 62,404 triangles；腾讯跨街日景为 259 / 61,962，夜景为 259 / 62,404。全部沿用 `<300 calls / <90,000 triangles` 原门槛，并检查热身后几何和纹理没有持续增加。

静态合批直接把索引源和非索引源写入最终属性数组，避免先展开、克隆、变换再合并的重复拷贝；特殊属性继续使用原路径。标准位置、法向、切线、归一化整数和自定义属性均与独立旧算法逐属性对照，源几何保持只读。面平面在相机首次需要时计算并缓存，远处和双面部件无需在启动时计算。通用楼体取消中间的逐格烘焙，只在最终共享批次烘焙一次。

完全隐藏的部件范围首次清除后不再逐三角形扫描；重建索引只遍历参与当前相机绘制的范围，并保持原顶点顺序。完整且不重叠的范围采用此路径，其他范围保留原全扫描处理。每次仅向 GPU 更新实际绘制的索引前缀，复用同一更新范围对象；空视野保留此前尚未消费的上传状态，后续非空相机重写有效前缀，首次创建和上下文恢复仍上传完整缓冲。独立旧算法与 GPU 缓冲状态模型覆盖相机、材质侧面、阴影、隐藏、毁坏及恢复后的逐索引一致性。

专门的稀疏可见 Node 基准包含 512 格、196,608 个三角形和 2.36 MB 索引，连续切换 120 次相机并重复五轮。索引计算中位数由 83.183 ms 降至 2.307 ms，模拟后续索引更新量由 283.1 MB 降至 0.916 MB；首次完整缓冲上传仍保留。这些是该基准的 CPU 和数据量，不能当作游戏帧率或真实 GPU 时间。

加载器提前请求五份地图和 Rapier，在主游戏包下载和同步规划时继续传输；失败保留原加载错误与重试流程。水域环按空间带建立索引，道路、建筑和园路预计算线段；放置阈值只在已经确定不合格时提前结束，远处边界用保守包围盒跳过，交通设施使用局部家具索引。五份地图独立完整数组对照为 5652 个装饰点、18373 段路缘、120 个标志和 37 个路口，均与旧版相同；水域 14,973 个边界和附近点的判断也保持一致。

第一次集成复测使用 Apple M1 Pro / ANGLE Metal、手机视口、禁用网络缓存、Fast 3G（1.6 Mbps 下载 / 750 Kbps 上传 / 150 ms RTT）和 4 倍 CPU 节流。旧路径静态合批约 4.546 秒，直接烘焙后约 2.710 秒；街道规划由约 2.337 秒降至 1.382 秒。直接烘焙版本两次真实首帧为 16,764 / 16,947 ms，同条件 Git HEAD 无 profile 对照为 19,044 ms。相应 `district:first-frame` 标记为 14,917 / 14,980 ms，尚不能满足包括点击后两次 RAF 的 15 秒门槛。另一次 HEAD profile 出现约 5 秒的音频恢复异常，已补正常对照，不用该异常样本计算收益。

## 2026-10-10 刚体步进与共享可见性

本轮先采样连续骑行的 CPU 调用树，再处理实际热点。沿用 [WebGL 最佳实践](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)的减少重复工作和缓冲上传方向，以及 Rapier 公开的 [PhysicsPipeline.step](https://rapier.rs/javascript3d/classes/PhysicsPipeline.html)。现有 Rapier 本来就是 Rust/WASM；继续降低绑定层开销比重写整个游戏更直接。

### 刚体世界

Rapier **0.21.0** 的 `World.step` 在完整物理步进后无条件调用 `mapNewSoftBodies`，扫描刚体、碰撞体及关节的 JS 包装对象，以同步软体撕裂产生和删除的对象。街区没有软体，公开的创建、删除和快照恢复 API 已维护这些包装对象；医院连续骑行的初始 CPU profile 中，`World.step` 累计约 1,068 ms，其中这次同步约 1,045 ms。

`physics/stepWorld.ts` 在没有软体时直接调用同一公开物理管线，保留原步长、重力、求解、CCD、场景查询更新、事件和 hooks；存在软体（包括禁用的软体）时回退官方 `World.step`。街区骑行、街道车辆、广州塔和地铁室内复用它，不合并或删除原有步进，不降低物理频率。升级 Rapier 时必须复核 `World.step` 的新增职责并运行真实 WASM 等价测试，不能把该优化当作所有版本的通用替代。

独立浏览器专项基准使用 4,002 个碰撞体和一个运动学体，每轮 120 步；热身后交替执行两个路径七轮，官方同步次数为 840，优化路径为 0。中位耗时由 53.1 ms 降至 0.8 ms，最终物理快照逐字节一致。该结果来自以静态碰撞体为主的物理专项，不能换算成游戏帧率或复杂动态场景的固定提升倍数。

真实 WASM 回归覆盖动态／运动学运动、CCD、角色扫掠和查询、碰撞体禁用／变形／移动／删除／重建、快照恢复、两种关节及级联删除、碰撞／接触力事件、hooks，以及软体启停、撕裂后生成对象的有效性和全部移除后的快速路径。Vitest 仅对 Rapier 精确启用依赖内联，保证 WASM 及 JS 回调使用同一模块实例。

### 静态合批

原来每个范围都会沿祖先链检查显隐，很多范围共享同一个空间格。现在初始化时编译共享祖先树，每个实际渲染 pass 按需读取可见分支；隐藏子树首次清除后直接跳过，叶范围显隐真正变化才重建索引。不能按显示帧缓存显隐，因为反射、阴影等相机可能临时切换它。静态网格的逆矩阵只在世界矩阵变化时更新；父级移动、旋转和镜像仍精确失效。完整边界、破坏 ID、原始顶点顺序、材质侧面及上传前缀行为保持。

稀疏城市专项包含 512 格、8,192 个部件、98,304 个三角形，24 格可见，每轮 240 次主画面／阴影相机回调。两个版本使用独立 Node 进程，热身后各七轮并交替复测：原路径中位数 23.76／24.88 ms，优化后 17.17／18.33 ms，减少约 26%–28% 此基准的 CPU 时间。最初的全节点缓存实现曾比原路径慢，已改为隐藏子树短路；不根据祖先读取次数单独声称性能提升。既有逐索引参考、模拟 GPU 上传、反射／阴影、破坏恢复及射线对照继续通过。

## 2026-10-10 WebGPU 迁移前原型基线

用户选择先完成主线性能优化，再以独立原型验证 WebGPU。本轮使用实际安装的 Three **0.186.1**、仓库已有 Playwright 与 TypeScript，显式执行 `requestAdapter`、`requestDevice`，取得 `GPUCanvasContext`，等待 `renderer.init()`，并要求 `renderer.backend.isWebGPUBackend === true`。本机返回 Apple **metal-3**、`isFallbackAdapter=false`，实际后端为 `WebGPUBackend`，启用了 `timestamp-query`；设备与页面错误均为零。这份迁移前记录没有把 WebGL 回退计作 WebGPU；当时尚未提供生产开关。现有开关和迁移后的验证见下一节。

第一轮原型将当时的静态合批与原始网格在同一标准材质场景逐像素对照，覆盖主视角、镜像相机视角、正交相机、真实方向光阴影、破坏／恢复及共享祖先隐藏／恢复。**21 项中 14 项通过，7 项 FrontSide＋阴影失败**；无阴影的 7 项完全一致，DoubleSide＋阴影的 7 项通过（镜像视角仅 1 像素差值大于 2）。FrontSide＋阴影主视角有 22,707／65,536 像素差值大于 2，平均 RGB 绝对差 26.87，图像侧面丢失。实测回调显示，主画面选择索引后，嵌套阴影的 `onBeforeShadow`／`onBeforeRender` 再改写同一索引，主画面随后使用阴影视角的内容；阴影 `onBeforeRender` 接收的原始 FrontSide 材质也不能代表最终 override material 的有效 side。迁移需要独立的 pass 索引资源和回调适配，不能用改成 DoubleSide 掩盖差异。镜像相机测试没有实现或验收游戏水面。

上传计数来自真实 `GPUQueue.writeBuffer`，静态索引的实际绘制前缀同时通过 GPU buffer 回读，全部与 CPU 索引一致。每组 60 帧的结果如下；两种 usage 在破坏与恢复时均各产生一次必要上传。

| 上传场景 | DynamicDrawUsage | 以 version 更新的 StreamDrawUsage |
| --- | ---: | ---: |
| 静止静态合批索引 | 0 次／0 字节 | 0 次／0 字节 |
| 移动相机，索引 version 变化 4 次 | 4 次／135,648 字节 | 4 次／135,648 字节 |
| 材质每帧变化，索引 version 不变 | 60 次／2,211,840 字节 | 0 次／0 字节 |
| 静止实例矩阵 | 60 次／245,760 字节 | 0 次／0 字节 |
| 实例矩阵每 6 帧变化，version 变化 10 次 | 60 次／245,760 字节 | 10 次／40,960 字节 |

该版本的 `NodeMaterialObserver` 会跳过无需几何更新的静态帧；`DynamicDrawUsage` 的重复上传发生在完整刷新等路径，不能概括成所有静态索引每帧都上传。实例动态属性、自定义 node、材质变化与多 pass 应分别测量。独立 256 盒子、256×256、DoubleSide、无阴影模型的提交 CPU 中位数约 0.4–0.5 ms、GPU timestamp 中位数约 0.104–0.115 ms；usage 间的计时波动不足以证明稳定加速。本轮没有游戏级 WebGL／WebGPU A/B，也不将模型耗时换算成游戏性能提升。

材质实测同样阻止直接替换后端：`onBeforeCompile` 与 `material.onBeforeRender` 均未调用，`object.onBeforeRender` 有调用；`ShaderMaterial` 输出黑色并报告不兼容；旧 `Reflector` 渲染时报 `buffers` 未定义。按 [Three WebGPURenderer 迁移说明](https://threejs.org/manual/pages/webgpurenderer.html)，现有 GLSL、`onBeforeCompile` 定制、呈现与水面反射／折射需要迁移为 node／TSL，并保留原有深度坐标、折射厚度和捕获调度。

下一阶段开放用户切换前，必须完成上述材质与多 pass 视觉等价；建立所有游戏入口及预览的一致异步 renderer 初始化，分别显示用户选择与实际后端、提供明确的不可用／回退原因；保存当前进度并安全重建画布与 GPU 资源，按 [Renderer 生命周期接口](https://threejs.org/docs/pages/Renderer.html)处理设备丢失与恢复；最后在相同场景、画质、分辨率和目标设备上比较 WebGL／WebGPU 的启动、CPU／GPU、帧间隔 P95 及资源使用，再决定默认后端。

## 自动选择与用户切换 WebGL／WebGPU

画面设置现在提供「自动（按设备选择）／WebGL／WebGPU」，沿用 `dayun-kicker.display.v1`。旧设置自动补齐 `renderer: "auto"`。实际状态由主场景发布，车库预览不覆盖该状态；更改选项先保存，点击「保存并重新载入」后生效。分辨率与帧率仍即时更新。重新载入会重新进入场景并结束当前比赛或联机；街区先保存自动进度，桌面端再等待磁盘确认。捕获失败、存档受保护、磁盘失败或 10 秒超时都会保留页面并允许重试。

| 选择 | 实际启动行为 |
| --- | --- |
| 自动 | 检查 WebGPU API，取得实际 adapter 和 device，初始化真正的 WebGPUBackend；成功后使用 WebGPU |
| WebGL | 直接启动现有 WebGLRenderer，不请求 adapter 或下载 GPU 运行时 |
| WebGPU | 尝试相同的真实 GPU 初始化，保留用户偏好；不支持或失败时使用 WebGL，并显示原因 |

adapter 不可用时不会下载 WebGPU 包。WebGPU adapter、device 和运行时初始化尝试最多 8 秒，超时晚到的设备、画布和渲染器会清理；这不代表整个场景的首次可玩时间上限。Three 内部 WebGL fallback 不计作 WebGPU，统一重新构造原 WebGLRenderer。能力检查选择可运行的后端，没有同时启动两套完整场景测试谁更快。WebGPU 并不保证每台设备、每个视角都获得更高帧率；遇到性能差异可手动选择 WebGL。

WebGPU device 丢失时暂停输入和音频，保存街区进度并确认落盘；保存及恢复标记写入成功后，重新加载为一次 WebGL 恢复启动，失败时留在页面提示重试。用户原偏好不被覆盖。WebGL context 恢复继续沿用原地恢复流程。开发诊断显示真实 drawCalls，GPU 模式跳过依赖 WebGL 私有接口的计时器。

兼容迁移包含 TSL 天空与远平面云层、地面材质、总部 atlas、玻璃、广州塔局部雾、交通接触阴影，以及 HDR 呈现、水面和后视镜。水面继续按高度共享、按距离和频率捕获，使用 WebGPU 的深度区间、纹理 Y 方向和真实斜切逆投影保留水下厚度吸收。HDR 保留原高光、饱和度和暗角；WebGPU 使用其支持的 4x MSAA。普通 Three PBR 材质仍由后端转换，现有 WebGL shader hook 保留。实现遵循 [Three 的 WebGPU／TSL 迁移说明](https://threejs.org/manual/pages/webgpurenderer.html)，没有修改私有 NodeLibrary 或伪装渲染器类型。

静态合批的 GPU 主画面、阴影、反射各自保留独立索引，顶点数据共享，嵌套 pass 后恢复父 geometry；最终阴影 side 与实际 override 一致。每个 view 缓存相机、变换、祖先可见性和破坏状态，静止主画面／阴影连续 20 帧索引 version 不变。动态阴影冻结使用一次注册的灯集合，新增／移除子树和之后开启 castShadow 都会维护注册，不在每个次级 pass 遍历整座城市。

原型的 21 组真实 GPU 图像复测全部通过，原来失败的 7 组 FrontSide 阴影已修复。重现可运行 `DAYUN_WEBGPU_VISUAL_ONLY=1 DAYUN_WEBGPU_OUTPUT=/tmp/dayun-performance-webgpu-switch node scripts/performance/webgpu-prototype/run.cjs`；此原型只激活标准材质合批协议，完整材质和水面由游戏 E2E 验证。历史上传和微基准数字属于迁移前实现，不作为新版游戏加速结论。

新增 `e2e/render-backends.spec.ts` 与 `e2e/render-backend-settings.spec.ts` 覆盖真实 WebGL→WebGPU→自动切换、偏好和实际状态分离、保存失败不重载、两种 GPU 偏好在 API 缺失时回退、实际反射／水下捕获与遮挡恢复、完整街区运行，以及 device 丢失后存档坐标和一次 WebGL 回退。本机 Chromium／Metal 无需 `--enable-unsafe-webgpu` 即可运行游戏，桌面 1280×720 与手机视口 390×844 已检查，页面标题、画面、设置交互、溢出、运行时错误和截图均通过。实体手机、其他 GPU、Safari／Firefox 和重新打包的桌面客户端仍需各自验证。浏览器插件未提供，本轮使用仓库 Playwright，证据保存在 `/tmp/dayun-webgpu-e2e/`。

## 启动门禁按场景区分

2026-10-10 提交前复测再次触发原 15 秒断言：首页按钮就绪 **12,019 ms**，比赛真实首帧 **27,777 ms**，完整街区真实首帧 **44,151 ms**。已获得维护者授权，按首页、比赛和完整城市区分回归预算；此前段落记录原门槛下的历史结果，以本节为当前规则。

[Google 当前 Web Vitals 指南](https://web.dev/articles/vitals) 的良好体验门槛包含 LCP ≤ 2.5 秒、INP ≤ 200 ms，按真实用户第 75 百分位验收；这些指标与完整游戏首次可操作时间不同。较早的 [RAIL](https://web.dev/articles/rail) 为普通网页慢速移动网络首次交互提出约 5 秒目标，并建议只加载最少初始内容、延后其他工作；它也不能推导出完整 3D 城市必须在同一时间内全部加载。[Unity Web 渐进加载指南](https://docs.unity.com/en-us/engine/7000.0/manual/platform-specific/webgl/building-distribution/web-optimization/progressive-asset-loading) 建议轻量初始场景、按需资源和异步场景切换，没有给完整游戏指定统一 15 秒上限。下列数字来自本项目实测和 CI 余量，**不是业界标准**；首页体验仍需继续优化，放宽场景回归上限不代表解决了长等待。

| --- | --- | --- |
| 首页按钮可操作 | 15,000 ms | 保留现有首页门槛 |

## 2026-10-12 转动视角优化与性能读数

本轮覆盖街区、城市合作及 macOS 桌面渲染路径。代码验证完成后，按用户继续指令在负载回落的窗口串行执行正式 A/B。出生点首次转视角和城市联机的长帧明显减少，macOS 尾帧改善；持续 CPU 收益因环境而异，不能概括为全面提速。下方“诊断样本”表属于较早的受污染数据，正式结果见本节后半部分。

静态合批按相机缓存面朝向判断，只有透视视点位移／正交视向变化小于所有相关面平面的安全余量才复用；透视相机纯旋转不改变面朝向，但视锥仍需更新。跨过边界、材质 side 变化、镜像／正交视角和破坏状态变化仍执行原判断。视锥、可见性及必要索引上传继续生效，参考算法测试逐面比对结果。没有降低几何细节、阴影、水面效果、实际缓冲分辨率或物理频率。

### 改动与正确性边界

- 原生回调记录将残余尾帧定位到接近目标期限的提前回调被拒绝。限帧准入允许至多 2 ms 的提前余量，并用重复回调保护避免同一周期重复提交；余量不计入已过期截止时间的推进。高刷新率、时间量化、长暂停和重复回调均保留回归，帧率上限与物理规则不变。
- WebGPU 四朝向改用实际绘制准备所需管线，删除重复的显式编译与额外准备工作；阶段间让出主线程，保留真实 HDR target、世界、阴影和水面。准备前同步实际 target 尺寸，完成／失败时恢复相机、临时可见性、原水面状态和采样状态。首次加载之后重新对齐游戏时钟，不把加载空档累计为游玩更新。

- 本地步行骑手增加有上限的躯干弹性与头部跟随，保持根位置、根朝向、腿与脚原运动；减少动态效果和暂停／瞬移时复位。真实 cockpit 与烘焙世界模型均有资源共享／可见性回归，后者检测不到独立脸部时不单独移动头盔。
- 独立城市联机页面新增自有 HDR target 与最后的呈现工作；嵌入街区的挑战借用已有 resolve。共享与自有对象分别恢复／释放，HDR 不支持时保留直接绘制。新增城市呈现有显存与 GPU 成本，本轮未独立测量其显存字节，不能以 JS heap 推断 GPU 内存收益。

## Windows 长距离骑行与追击（2026-10-14） {#windows-2026-10-14}

本轮针对当前 Windows 11 x64、RTX 4080、Electron 44.7.0／Chromium 152，验收实际跨街区骑行的最低完整一秒帧数不低于 60。原生窗口 harness 使用 WebGL、1440×900 缓冲、DPR 1、90 FPS 上限、白天晴天、第三人称、HDR 半浮点目标与 4× MSAA，保留既有阴影、水面和物理频率。默认 60 FPS 上限未改变；本机在该上限下会出现完整一秒 59 帧，因此验收使用已有的 90 FPS 设置留出余量，不能将 59 四舍五入为达标。此范围不覆盖更大的全屏缓冲、其他 GPU 或全部天气。

冻结完整应用源码后，先定位到灯光数量随远处建筑隐藏发生变化，跨区域首次使用新配置触发约 2.1–2.3 秒着色器编译。修复将两盏庭院灯保持注册，远处强度归零，避免全场景灯光配置反复变化。单独扩充预热未消除该停顿，失败记录保留；原生 WebGL 预热仍覆盖主场景与水面捕获的实际层级、雾状态，并在成功或失败后恢复场景。代价是远处仍保留两盏零强度灯及加载阶段的编译工作，不能宣称额外计算为零。

追击原有路网规划间隔为 0.65 秒，直接追击仍使用上次规划的玩家位置，接近该位置后会短暂停住；警察显示又随普通路人按 30 Hz 重建。现在可通行的近距离末段逐模拟步跟随玩家，仅警察的 14 个实例部件逐渲染步更新，保留路网规划、碰撞检查与拦停流程。远距离路人和车辆的更新频率不变，绘制调用未增加；额外代价为近距离通行查询和少量矩阵／颜色上传。

## 2026-10-20 GPU 受限：几何切块与墨线计算 {#gpu-bound-2026-10-20}

本轮排查 Godot 原生客户端在大缓冲下的 GPU 受限帧。Apple M1 Pro（16 核 GPU）／32 GiB／macOS 26.6.2，Godot 4.7.2 Forward+ Metal，线程模型 Safe，关闭 VSync、不限帧。窗口 2560×1440 时实际帧缓冲为 4609×2592，窗口 1280×800 时为 1280×800。视角固定在 M2 固定包的客村骑手站街景，隐藏 HUD、物理开启。4609×2592 下渲染录制 CPU 约 0.8–0.9 ms，帧时间由 GPU 决定。Metal 没有可用的 GPU 时间戳；整机 GPU 读数来自 IOKit 整机利用率，不代表游戏本身的 GPU 时间。

### 已证实的热点与改动

- **合并网格让阴影级联剔除失效。** 区域美术按「区域 + 材质」合并成跨约 1.2 km 的网格，全城灰盒道路、标线和铁轨又合成单个 MultiMesh。包围盒覆盖所有级联，每个级联都整体绘制：阴影通道每帧约 336 万图元，可见通道约 91.5 万。美术导出端把跨度 ≥384 m、≥2,000 三角形、属性限于位置／法线／UV／颜色的合并组按 256 m 瓦片切分；盒子批次改为按「材质 + 256 m 瓦片」分组。之后阴影约 90 万图元，可见约 46 万。
- **墨线读屏幕纹理触发整帧颜色拷贝。** 透明队列中的全屏四边形使用 `hint_screen_texture`，渲染器每帧拷贝整块颜色缓冲，4609×2592 下约 1.0–1.3 ms，四边形本身另约 0.4 ms。改为主相机上的 CompositorEffect 计算 pass，在透明物体之前原地处理颜色缓冲；每个像素只读自身位置的颜色，不再需要拷贝。

两项改动都保持实际缓冲尺寸、渲染比例、画质档位和物理逻辑，没有提高任何预算。

### 诊断：逐层关闭（非验收）

同进程 ABBA，4609×2592、22 时普通氛围。只用于定位和排序，不计入收益。部分时段另一个会话的渲染测试在并行运行，这段读数偏高，只作排序参考。

| 关闭的层 | P50 变化 |
|---|---|
| 墨线（四边形、屏幕拷贝与运算） | −2.1～−2.3 ms；屏幕拷贝约 1.0–1.3，四边形约 0.4，采样与运算约 0.4 |
| 日照阴影 | −1.95～−2.2 ms；硬／软过滤与图集 4096→2048 只差 0～0.2 ms |
| 辉光 | −1.1 ms；改线性上采样只省约 0.15 ms，且改变画质 |
| SSAO（已是半分辨率低档） | −0.76 ms |
| 据点点光／车灯 | −0.35 ms |
| FXAA | −0.28 ms |
| 天空、雾、光池、夜景、标签 | ≈0 |

1280×800 下关闭阴影仍约 −2.4 ms，代价与分辨率无关；调过滤和图集几乎无效，说明阴影属几何受限，由此指向剔除粒度，而不是阴影分辨率。

### 正式 A/B 的条件与门槛

- 基线为改动前冻结的完整工程副本，包含当时共享工作区的未提交改动，另存文件哈希。
- 每个窗口 300 帧，前置 30 帧预热；5 个时段（12／17／18／22 时与 22 时雨）× 3 种氛围，氛围顺序轮换。高分辨率每进程 2 轮，低分辨率 1 轮。独立进程按 A B B A A B 串行交替，每版 3 个进程。
- 门槛在看结果前写定：P50 改善 ≥0.4 ms 且至少 2／3 配对同向；P95／P99 变差不超过 0.5 ms；长帧不超过基线 +2；就绪变差不超过 150 ms；画面差异处于噪声水平。
- 运行时有其他 Godot 进程、屏幕锁定或窗口失焦的样本剔除，不补造结果。

| 改动／帧缓冲 | P50 ms | P95 ms | P99 ms | >33.4／>50 ms 帧（A→B） | 配对 ΔP50 ms |
|---|---:|---:|---:|---:|---|
| 美术分块，4609×2592 | 10.15→9.07 | 13.25→12.36 | 13.64→12.71 | 0/0→2/0 | −1.07、−1.11（第 1 对基线失焦，剔除） |
| 美术分块，1280×800 | 5.14→4.20 | 7.59→6.45 | 8.04→6.89 | 0/0→0/0 | −1.01、−0.94、−0.83 |
| 墨线计算，4609×2592 | 9.09→8.26 | 12.33→11.23 | 12.67→11.59 | 1/1→0/0 | −0.80、−0.84、−0.85 |
| 墨线计算，1280×800 | 4.07→3.73 | 6.27→6.09 | 6.74→6.51 | 0/0→0/0 | −0.45、−0.34、−0.30 |

表中为各版 3 个进程的窗口中位数，每版高分辨率 27,000 帧、低分辨率 13,500 帧；美术分块高分辨率组剔除失焦对后，A 版剩 2 个进程。15 个时段／氛围条件全部同向改善，超过 16.67 ms 的帧占 0.0–0.1%。美术分块两种分辨率和墨线高分辨率组的 P50、P95／P99、长帧与画面都满足预设门槛；1280×800 墨线组 P50 中位数只改善 0.34 ms，低于 0.4 ms 门槛，只记为同向小幅改善。就绪一项见代价。

两项串联后，高分辨率 P50 约 10.15→8.26 ms（约 −1.9 ms，−19%），P99 约 13.6→11.6 ms。这是两组 A/B 的串联估计：墨线组的基线就是美术分块版本，复测为 9.09 ms；直接的「基线 vs 全部改动」组整组无效，没有独立验收合计收益。本组关闭 VSync、不限帧，且是固定机位，不是骑行路线或压力玩法样本；P99 低于 16.67 ms 不等于稳定 60 FPS 验收，也不外推默认显示同步或长途场景。

### 无效样本与未采用方案

- 一组在锁屏时运行：前台为登录窗口，帧全部失焦，低分辨率被系统节流到约 9.6 ms。整组未计入。
- 「基线 vs 全部改动」组运行时用户在使用其他应用，中途还锁屏，6 轮里 4 轮失焦，整组无效。其中唯一基本有效的一对 ΔP50 为 −1.93 ms，与两项分别测得的改善之和相近，只作一致性参考，不计入验收。
- 早先的运行时切块版本另有一组聚焦 A/B，高分辨率 −0.98 ms、低分辨率 −0.95 ms，与导出端方案一致；因就绪代价过高未采用。

### 代价

- **加载**：无头插桩的世界构建中位数约 547→559 ms（+12 ms，其中盒子批次 +8 ms），无头就绪 +5～30 ms。窗口模式各组就绪中位数差 +21～+190 ms，波动与同期用户活动同时出现；上限超过预设的 150 ms 门槛，本轮以无头插桩判断实际构建代价，窗口就绪没有另做无干扰复测。运行时切块版就绪 +205～224 ms，因此改为导出端切块。
- **CPU 与绘制数**：渲染录制 CPU 约 0.81→0.89 ms；可见绘制约 436→560，阴影绘制约 560→600–640。切块用更多绘制换取更少图元，本机为 GPU 受限，CPU 较紧的设备需另测。墨线改动对 CPU 无明显影响。
- **美术产物**：区域模型 52.2→51.0 MB，多数块不足 65,536 顶点，索引改为 16 位；网格 158→454 个，三角形 666,264 个与碰撞体 4,227 个不变。美术需要重新导出（约 1 分钟），Godot 重新导入约 3.7 分钟（一次性）；未重新导出前画面正确，但没有分块收益。
- 显存与长时间运行内存未测量。

### 画面与行为核对

氛围视角测试的 48 张截图与基线自身两次运行的差异对比。

- **美术分块**：街景差异在基线噪声内（>2/255 的像素 ≤0.005%）；远景差异只出现在按时间动画的 LED 立面和探照灯上，幅度与基线两次之间相当。
- **墨线计算**：街景每张 0–10 个像素不同（≤22/255），画面四边一致；「彩色」风格夜景截图正常。移植时修正三处：`source_color` 默认墨线色在渲染时转成线性值，计算着色器同样转换；`RenderSceneDataRD.get_cam_projection()` 返回的投影已含反向 Z 修正，不能再乘一次；原着色器采样器为重复寻址，画面上下边的墨线由此产生，计算版沿用。
- **行为差异**：加速线的随机闪烁改用墙钟时间，图样一致、相位不同；只在加速时出现，未做像素核对。

辉光、SSAO 和 FXAA 只能靠降低画质节省，保持不变；阴影过滤档与图集尺寸调整几乎没有收益，天空、雾、光池、夜景和标签代价约为零，均未改动。切块后阴影仍约 1.4 ms（约 90 万图元，诊断值）；覆盖全城的共享单车 MultiMesh 诊断约 −0.3 ms，但实例是动态的，本轮未改。
