本文未实施新剧情、角色或世界系统，也未创建远程 Issues、里程碑或发布构建。现有 Godot《粥还热》候选继续作为可运行基线；双宿主职责、资源和发行验收仍遵循 [Godot 迁移计划](godot-migration.md)。

执行任务、优先级、依赖与勾选状态统一维护在 [游戏开发待办](development-backlog.md)。本文保存产品设计、剧情讨论和估算，不另维护同一批任务的完成状态。

## 1. 美术默认方向

采用“**低多边形体块 + 克制的漫画动作表达 + 温暖的广州街坊光色**”：

- 建筑、车辆、树木和街道设施延续现有程序建模，优先统一比例、轮廓、倒角、材质与模块复用。
- 人物、车辆、敌人与交互物通过清楚的轮廓和分档明暗保持可读；背景减少细碎墨线与密集网点。2026-10-21 起画面风格随世界切换：现实广州使用明快卡通，以细彩色描边为主，不加网点；进入丧尸世界后改用冷墨木刻描边与排线（[跟随世界的画面风格](cartoon-atmosphere.md#world-following-look)）。
- 日常世界以奶油色瓷砖、砖红、榕树绿、青绿遮阳篷和暖光建立生活气息。异世界复用地标与街巷，通过环境声、灯光、封路与少量变体物件制造差异，避免只靠全屏压暗表达危险。
- 丧尸世界已于 2026-10-20 选择 B「湿冷夜街」作调性参考：冷环境、暖色活人据点、清楚的敌人和通路。光照仍由当前游戏的时间与天气驱动；B 只描述夜间参考，白天与黄昏保留相应光照，不改用固定夜景或照搬生成图。接入约束见 [丧尸世界光照基线](game/world.md#infected-visual-baseline)。
- 踢击用短促闪光、动作弧线和夸张物理突出荒诞感；速度线和强烈视觉效果主要服务动作瞬间，并服从减少动态效果设置。
- 先精修骑手站、粥店与异常锚点附近的一段可玩街景。概念图中的店铺密度、树冠和立面细节属于资产制作工作，不视为已有实时效果或性能承诺。

本次五张生成概念图用于内部方向讨论，原图与提示词保存在源码工作区的忽略目录 `artifacts.local/concept-art-2026-10-17/`，不作为构建依赖或公开文档图片。若后续选为正式媒体，按 [COS 资源流程](media-assets.md)发布和校验。既有画面实现与历史边界见 [卡通画面氛围](cartoon-atmosphere.md)。

## 3. 五幕原案与验收

以下保留原案名称与标称时长；8 + 12 + 10 + 18 + 12 = **60 分钟**，已占目标上限，尚未给新手摸索、失败重试与探索留空间。不能把这一相加结果当作试玩时长已达标。

| 幕 | 原案时长 | 剧情与主要操作 | 发布不可缺少的验收 |
| --- | ---: | --- | --- |
| 序幕：今天不用加班了 | 8 分钟 | 玩家操控失业后的大云，从办公室外与手机消息开始，步行到陈叔处注册外卖员、领取电动车；背景随行动揭露 | 不读外部教程即可完成移动与交互，理解为何开始配送；不靠大段开场独白交代全部过去 |
| 第一幕：您的订单即将超时 | 12 分钟 | 接单、取餐、导航、订单计时、碰撞相遇、首次切换角色 | 完成至少一笔真实配送；认识外乡青年；切换后目标、车辆和任务状态正确 |
| 第二幕：不存在的收货人 | 10 分钟 | 异常订单、阿榕与调查影像、广州塔锚点、空间异常、首次世界切换 | 通过受控锚点到达同一城市的异世界；位置、朝向与任务延续遵守切换契约 |
| 第三幕：这里不是广州 | 18 分钟 | 躲避 / 潜行、拾取、巡逻与追击、基础近战、简易避难所 | 战斗或躲避均可完成必要目标；敌人寻路与同伴掉队不造成任务死锁 |
| 终幕：最后一单 | 12 分钟 | 程序员解析信号、阿榕指路、青年首次破界、限时逃生、父亲影像与片尾 | 完整逃生；失败可从终幕检查点重试；片尾悬念与试玩结束页可达 |

开发顺序以依赖和风险为准，先做第一幕配送与异常切换原型，不按五幕顺序逐个堆完资源。

### 参谋建议：把故事拴在“订单”上

1. **一个主问题贯穿五幕。** “这一单究竟要送给谁、送到哪一个广州？”可作为工作中的叙事钩子。失业、相识、调查和逃生都围绕订单推进，减少互不相干的开场介绍。
2. **让主角分工产生操作差异。** 程序员负责识别、整理和解读空间信号；外乡青年负责在关键节点对锚点采取行动、完成破界；阿榕负责影像证据、地标辨识和道路引导。具体身份与能力由后续剧情确定；不先做技能树或编程小游戏。
3. **首次切换要解决眼前的问题。** 碰撞相遇后让玩家分别完成一个短操作，共用步行、交互和骑行基础。避免只换模型、再看一段对话；也不让未操控角色必须实时赶路才能继续。
4. **异常应更早露头。** 原案约在第 30 分钟才完成首次跨世界。建议开场数分钟就留下可辨认的异常线索，并压缩铺垫，使首个可操作切换有机会在 10–15 分钟内出现。具体是否调整正式五幕时间，待首轮实玩定稿；切片可先截取和压缩这一段。
5. **保留具体的人情牵挂。** 《粥还热》的粥店、阿婆、陈叔、骑手站和救援可作为复用素材，让危机影响玩家认识的人。同一门口、招牌与路线在两世界中的变化，比新增大片废墟更有意义；不要求把原七单再完整玩一遍。
6. **终幕能力提前铺垫。** 青年正式破界留在终幕，但此前出现可观察、可试探的反应，让玩家知道要做什么，避免结尾突然获得一项未经表达的能力。
7. **只用一条主要限时压力。** 普通订单计时先给宽限与可理解的后果；异常调查和关键对话不被配送超时反复打断。终幕承担明确的逃生倒计时，暂停 / 对话 / 加载如何冻结须统一，失败从近处检查点重试。

以上是建议，不代表新增对白、世界观因果或能力规则已经确定。

## 4. 先做的 10–15 分钟垂直切片

切片应同时验证故事、驾驶、角色切换、一次世界切换与最小生存操作。只做配送加转场视频，无法验证完整方案。

| 连续步骤 | 暂定时长 | 要验证的内容 |
| --- | ---: | --- |
| 最短步行 / 交互引入 | 1–2 分钟 | 无文档引导、明确接单动机 |
| 一次接单 → 取餐 → 骑行 → 停稳交付 | 4–5 分钟 | 现有驾驶与导航是否支撑叙事节奏 |
| 相遇与一次剧情角色切换 | 1–2 分钟 | 角色有明确分工，输入、相机和任务不丢状态 |
| 异常订单 / 影像线索与接近锚点 | 1–2 分钟 | 玩家是否理解异常并愿意继续 |
| 可恢复的世界切换 | 约 1 分钟 | 共享位置、转场、加载失败与存档边界 |
| 一小段躲避 / 踢退与到达安全点 | 2–3 分钟 | 一种感染者、基础近战、失败重试和收尾 |

合计约 10–15 分钟，只是设计配额。先复用 **客村 / TIT 骑手站的一段现成配送路线**；广州塔作为正式剧情锚点保留。若塔边走廊尚不能满足这段节奏，先用现有安全点做开发锚点验证技术，不提前锁定塔边整片街区或扩大精修范围。

切片出口：新档连续可玩、两名角色各完成一次有意义的操作、切换前后检查点可跨进程恢复、最小遭遇可用战斗或躲避通过。收集新玩家完成时间、迷路点、死亡 / 重试、角色与世界规则理解情况，并检查选定样板街景的实际画面与既有性能门槛。

## 6. 技术落地原则

保留单一 Godot 游戏工程与现有目录。`autoload/`、`actors/`、`systems/`、`worlds/`、`chapters/` 是职责示意，不作为强制搬目录的任务；也不为每项职责新增全局单例。

| 职责 | 复用 / 扩展路径 |
| --- | --- |
| 会话与输入 | 扩展当前 `GameSession`；同一时刻只有一个受控角色和一个物理控制权威 |
| 剧情与任务 | 继续使用 `dayun-kicker-content` 的手写 JSON 与现有构建 / 节点执行链路；新 Demo 使用独立内容 ID，保留旧章 |
| Resource 的用途 | 可作为 Godot 侧生成数据或场景绑定的承载形式，不建立与共享 JSON 并行的第二套手写任务真相 |
| 角色 | 共用移动、交互、骑行与基础动画接口；身份和能力用数据 / 小组件表达，不复制两套控制器 |
| 世界 | 基础道路、坐标和稳定实体 ID 共用；现实 / 感染变体覆盖环境、道具、敌人与必要通路状态 |
| 战斗 | 从一种感染者和一种基础近战动作开始，关键任务不依赖随机刷怪或 NPC 恰好走到某点 |
| 存档 | 扩展当前白名单状态与版本迁移；不序列化场景树，不把内容版本冒充世界变体 ID |
| 内容分工 | 规则规格和 fixtures 共用；新玩法先在 Godot 验收，Web 不承担五幕同步实现 |

### 世界切换的最小契约

1. 只在剧情允许且可停稳的锚点发起；冻结输入和模拟计时，记录源世界、角色、车辆、任务与检查点。
2. 请求目标变体并验证资源、碰撞和必要任务点。可使用预加载与遮挡转场；不同时常驻两套完整城市，不先承诺完全无缝或通用地图分块。
3. 锚点在两世界中保持相同可站立空间，以保持角色位置和朝向。若目标空间无法满足契约，转场失败并恢复源世界 / 检查点，不静默传送到任意位置。
4. 目标可玩后一次性提交世界、任务与控制角色；转场触发和奖励必须幂等。加载失败、重复交互或退出重开不能得到一半现实一半感染的状态。
5. 在源世界检查点和已提交的目标检查点保存；中途退出回到最近已提交状态。覆盖角色在车上 / 步行、重复触发、资源失败、读档和取消输入。

世界视觉变化必须与敌人、碰撞、导航和交互状态一致，不能只切滤镜。目标变体是否需要重新生成局部寻路、车辆是否随行、同伴如何到达均在切片内明确。

建议的新增持久状态职责包括内容 ID / 版本、章节与节点、世界变体 ID、当前主角、各角色和车辆状态、关键物资、世界事实与已提交检查点；具体字段名和 schema 版本等实现设计后再定。

## 10. 后续待明确的问题

- 大云的房租压力与背景揭露如何呈现；周远的专业、当前工作、一次具体家庭争执与换角动机；破界的前兆、触发条件和限制。
- 阿榕摄影专题的具体切入点、父亲失踪时间与第一条有效线索；她全程参与的表现形式是现场同行、影像 / 通话还是分段会合，以及如何避免持续护送成本。详细已知与未定项见 [人物设定](game/characters.md#demo-cast)。
- 世界切换是否携带电驴、同伴与物资；两世界的时钟、可见线索与局部状态如何对应。
- 《粥还热》的事件哪些直接复用、哪些改写。2026-10-20 已确定阿婆救援与感染者都在丧尸平行世界，现实广州保持日常，见 [Demo 两章剧情设计](story-demo-chapters.md)；新世界规则仍不能直接等同于旧章的 `outbreakSeen` 标记。
- 破界逃生回到原现实还是第三种状态；父亲影像揭示一个明确事实，并留下哪一个长线问题。
- 发布版首个世界切换的目标时间、必要探索空间、目标 Windows 设备、实体手柄、团队投入与美术资源工时。

这些问题可随切片逐项解决，不阻止复用现有系统；会影响实现的规则需在对应模块开工前写入数据和验收规格。
