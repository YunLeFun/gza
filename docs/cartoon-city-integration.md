# 广州街区卡通材质接入（2026-10-14）

本轮把[街景样板](cartoon-sample.md)的三段明暗规则接入实际广州自由骑行。骑手服装与电驴、普通建筑及店铺的哑光表面、行道树和现有实例化车流使用同一组明暗级别；透明玻璃、金属、低粗糙度表面、带发光贴图的招牌以及自定义幕墙／地面／水面 shader 保留各自的材质与采样职责。图形风格改动不修改道路、碰撞、驾驶、物理步长、几何、实例批次、实际缓冲、阴影或水面刷新规则。

## 材质与资源边界

共享控制器在场景创建和换装等明确的边界注册网格，不逐帧遍历城市。原材质所有者继续驱动颜色、纹理、透明度和发光强度，转换材质读取同一份值，保留步行克隆与原骑手的外观同步。原材质发出 shader 失效后，转换材质也失效，覆盖货箱贴图从无到有等情况；按需加载的头盔和装备完成后再次注册。

行道树沿用原来的几何和顶点配色，只统一其已有卡通材质的 gradient ramp。车流中原本共享一个材质的实例批次继续共享，不为不同零件额外拆批。打印招牌和独立的玻璃／金属材质不被转换；原实例批次里没有独立材质的玻璃色块仍沿用原有批次结构。

清理时先恢复借用的原材质和树木 ramp，再让各工厂释放自己的资源。装备原材质销毁时同步释放对应转换材质，避免反复换装保留旧资源。新增贴图是程序生成的 3 × 1 ramp，没有新增媒体文件、下载或 COS 对象。

原有 HDR 色块归并与颜色反差墨线继续使用同一条呈现路径；本轮没有新增后处理 pass。以上资源与结构约束不代表新增材质零成本，成本需看正式对照和单独 GPU 诊断。

## 验证

四项控制器回归覆盖：制服颜色／货箱纹理／发光强度的实时同步；玻璃、金属、招牌及自定义 shader 的排除；树木 ramp 借用与恢复、按需网格注册；装备资源释放。骑行路径回归还验证“导航 sweep 返回可通行，但骑行实体持续停在原地”时使用正常倒车输入脱困，不改写姿态。

真实 GPU E2E 覆盖 WebGL／WebGPU 的骑行、上下车、手机视口、WebGL 丢失／恢复，以及水面和唯品会／TCL 玻璃幕墙。实际画面已检查两种后端的 TIT 西门与步行骑手。

最终版本的相关单测 5 文件／23 项、真实 GPU E2E 6 项、全仓类型检查、Web 生产构建、原有体积预算、发布文件校验、资源策略与 diff 检查通过。首屏 JS 为 321.4 / 350 KiB、CSS 为 15.9 / 16 KiB，街区入口为 471.5 KiB / 1 MiB，总游戏资源为 19.63 / 20 MiB；发布产物校验 556 个文件，诊断样板没有进入发布包。没有提高预算。公开文档输入检查、类型检查与构建也通过；完整 `release:check`、正式桌面包装和全部 E2E 未在本轮运行。

测量结束后的源码与冻结最终快照逐文件一致，锁文件／媒体清单的 SHA-256 与初始记录一致，共享包源码无改动。白天原版／卡通版使用同一站位截图，WebGPU 黄昏／夜景及手机视口分别检查，未出现 shader 错误。截图只作为本地实机效果交付，不进入 Git 或性能样本。

## 整城骑行对照方法

完整应用源码分别冻结为接入前和接入后快照；锁文件、资源版本与共享包在两组之间保持相同。两组使用同一版基准工具、同一份驾驶输入规划与真实碰撞查询。复用 `benchmark:camera` 的路线模式：从 TIT 西侧出发，依次经过广州塔、客村、丽园与腾讯广州大厦，计划道路长度约 7.04 km。实际路程、路线进度、横纵跨度、终点距离和运行状态都必须满足完整到达条件。

```sh
pnpm benchmark:camera --platform=browser --backend=webgl --scenario=district --motion=route \
  --route=canton-tower,kecun,liyuan,tencent --duration=600000 --rounds=1 --frame-rate=60 \
  --baseline=/absolute/frozen-app --output=/tmp/gza-city-toon-run
```

每个后端的原版与卡通版各三次独立进程，前后、后前、前后的顺序串行运行。完成路线后提前结束，最长 600 秒。固定 1440 × 900、1080p 设置、DPR 1、60 FPS 设置、晴天正午和原第三人称驾驶；不使用自适应分辨率抵偿成本。记录实际 HDR／MSAA／阴影、缓冲与后端，拒绝回退、尺寸变化、运行时错误和未完整到达的样本。

CPU 分别列出世界渲染提交的墙钟时间，以及动画回调入口到 HDR 呈现结束的墙钟时间；后者包含路线输入规划与碰撞查询，不是进程 CPU 利用率。帧间隔报告 P95、P99、长帧发生率与最低完整一秒帧数。ready 是开发页面从导航到正常 ready 状态的耗时，新进程不保证磁盘或驱动缓存完全冷。

### 预跑失败与修正

最初的 360 秒预跑在约 4.04 km 路线进度、丽园附近停止移动，未到达终点。该失败保留在 Git 外，不能算作整城验收。原自动驾驶只在导航查询找不到路径时倒车；真实骑行约束与导航 sweep 的差异可以使实体停住。基准驾驶器现在在连续两秒几乎不移动、低速且未到终点时使用三秒正常倒车，清除旧绕行目标再规划，仍保留游戏的碰撞、警察与拦停。

修正后，TIT—丽园—腾讯的 3.70 km 定向路线在约 189 秒完整到达，实际骑行 3.61 km。这个不同路线的预跑只用于验证工具，不混入上述完整路线正式对照。

原始数据、截图、冻结源码与失败日志留在 Git 外；公开文档只记录汇总和方法。

### 正式结果

环境为本机 Apple M1 Pro、Chromium 156.0.8078.4、ANGLE Metal。每个后端独立运行三组，全部十二次完成计划路线，实际骑行 6.921–6.968 km，横向跨度约 2.535 km、纵向跨度约 1.087 km，结束仍在第三人称电驴骑行。没有运行时／shader 错误或后端回退。每轮实际缓冲始终为 1440 × 900，HDR 半浮点目标、4× MSAA 和阴影一致；WebGL 另记录到 antialias 为 true，WebGPU 的这一独立布尔读数未提供。

### 单独 GPU 诊断

正式矩阵完成后，在 TIT 西侧固定骑手位置与朝向，另开四个独立进程，每版／后端采 120 帧。两种后端均有实际时间戳支持，120 / 120 帧有效，缓冲为 1440 × 900。该短窗口含 GPU 计时探针，不能混入全程验收，单次局部结果也不能推广为整城 GPU 收益。

| 后端与计量范围 | GPU P50 前 → 后（ms） | GPU P95 前 → 后（ms） |
| --- | --- | --- |
| WebGL，整帧 timer query | 6.104 → 5.839 | 6.560 → 6.220 |
| WebGPU，属于本游戏帧的 render pass 时间之和 | 11.010 → 9.961 | 17.105 → 14.942 |

两种计量范围不同，不用此表判断哪个后端更快。WebGPU 固定视角前后都是 232 次绘制、76,701 个三角形、431 个几何，纹理读数为 70 → 71。这个视角的 GPU 时间下降与全程回调 CPU 中位数增加同时存在；本轮尚未对尾帧或提交成本进一步归因，不能把简单明暗 shader 等同于整机提速。

## Three.js、Godot 与同构

本轮继续使用 Three.js，Web 与现有 Electron 桌面客户端共享同一套 TypeScript 场景、规则、UI、存档和资源流程。卡通渲染本身可以在两种引擎实现；平台、内容制作流程和已完成的集成决定这次选择。

Godot 是后续原生桌面内容制作的候选，适合需要编辑器场景制作、骨骼动画、原生打包和更复杂 3D 工作流时进一步验证。当前独立 Godot 实验已有原生城市与人群压力测试，但生产任务、账号、存档、全部武器和网络权威仍未证明等价，现有数据不能直接宣布全项目迁移收益。Godot 官方当前说明 Web 导出使用 Compatibility／WebGL 2，Forward+／Mobile 不支持 Web，尚无 WebGPU：[Web 导出文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)。

如果未来用 Godot 原生客户端配 Three.js 网页客户端，先共享地图、资源版本、任务定义、协议和存档 schema，并使用共同的玩法 fixture 验证一致性。TypeScript 代码不会自动成为 Godot 的同一份执行逻辑，需要明确的共享核心或移植适配；这会增加两套渲染和平台实现的维护成本。当前建议保持单一 Three.js 运行时，不在本轮同时扩建第二套生产玩法。
